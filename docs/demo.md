# 演示与面试准备

## 60–90 秒演示

1. 0–15 秒：说明消费 `/latest`，用历史值检测，再生成规则或可选模型解释。展示 `python run.py`、`/status`，确认 sensor_ok；数据源需先启动。
2. 15–35 秒：展示时间线和 `/alerts`，指出 8 次历史暖机与 baseline_mean/baseline_std/baseline_count/threshold，说明当前值没有参与自身基线。随机源暂无异常时如实展示空列表。
3. 35–55 秒：执行 `python -m unittest discover -s tests -v`。本地假传感器先给 8 稳定值再给突变，验证不依赖随机等待；慢模型检查验证 HTTP 仍响应，队列满则规则回退。
4. 55–75 秒：执行 `python scripts/evaluate.py`，展示三场景。孤立突变 F1 从 1 降到 0.75，持续偏移召回仍低，不能只展示改善数字。
5. 75–90 秒：解释 configured_mode 与 explanation_mode/fallback_reason；未准备真实 Ollama 就明确只验证受控替身。下一步需要真实数据标定和硬件联调。

Windows/POSIX 启动命令见 README。现场先运行测试，确认环境和端口可用。

## 面试问题

- 为什么先加入当前点会漏检？它改变自己的均值和标准差；8 个恒定历史加突变的测试能复现稀释。
- 标准差下限有什么意义？避免除零及极小噪声被放大；下限在指标原单位中定义，需按传感器标定。
- 为什么持续偏移仍漏报？异常值进入历史，基线逐渐适应；这里没有冻结基线或漂移检测。
- 重复帧如何处理？驻留节点只接受 ts>last_ts；坏帧不更新时间。淘汰或重启后重新暖机，设备时钟需要上游约定。
- 只限制窗口够吗？无穷新节点仍会扩大字典；同时限制节点数并删除对应时间戳。
- 慢模型会阻塞吗？最多 1 执行+32 等待；网络在锁外，满队列规则回退，检测和读取可继续。
- 为什么不宣称准确率提升？更敏感也更易误报，三种合成场景不足以说明泛化；需要业务标注和成本权衡。
- 标签是否泄漏？布尔标签单独存储，特征帧没有标签，多个指标触发只计一个样本。
